# CajeerLogs 0.1.2 — Migration Engine

PostgreSQL 17/18, PHP 8.4+. Существующие SQL-файлы `0001`–`0008` и их SHA-256 не меняются. В 0.1.2 сам runner создаёт три служебные таблицы: `schema_migration_state` (каталоговый эталон и хеш истории), `schema_migration_runs` (последнее состояние, количество попыток и batch), `schema_migration_attempts` (история каждой попытки, время, длительность, категория ошибки). Они сохраняются в обычном PostgreSQL backup. Не редактируйте их вручную.

## Обновление 0.1.1 → 0.1.2

1. Сделайте backup средствами **старой версии** и сохраните `.env`, ключ TOTP, TLS и внешние секреты. Остановите прием событий и фоновые сервисы; SDK должны сохранить неподтвержденные события для retry. При контейнерной установке выполните backup из старого образа.
2. Наложите архив изменённых файлов на текущий проект; при Docker пересоберите образ и запустите команды из нового образа. Не запускайте API/worker новой версии до окончания миграции.
3. Запустите:

```sh
php bin/cajeer version
php bin/cajeer migrate:plan
php bin/cajeer migrate
php bin/cajeer migrate:verify
php bin/cajeer db:doctor
php bin/cajeer doctor
```

`migrate:plan` до первого запуска на старой БД покажет `unverified` и может показать пустой список pending SQL. Это нормально: 0.1.2 должен создать структурный эталон, а не повторить уже применённые SQL. Для legacy history runner под общей блокировкой строит отдельную случайную **пустую reference-схему внутри savepoint**, выполняет в ней только доверенные применённые SQL-файлы, сравнивает каталоги целевой и reference-схем, затем откатывает savepoint. Данные production не копируются и не изменяются этим сравнением. При несовпадении метаданные не закрепляются, миграция останавливается. После успешной проверки эталон и служебные таблицы коммитятся.

### Роли и права

Если используются `DB_MIGRATION_USERNAME`/`DB_MIGRATION_PASSWORD`, передайте их только из защищённого окружения доверенной CLI-команды (см. [PostgreSQL Runtime](PostgreSQL-Runtime.md)). Для первоначальной adoption уже установленной базы migration role должна иметь право `CREATE` на БД (возможность создать reference-схему) и владеть объектами приложения. DBA может временно выполнить `GRANT CREATE ON DATABASE cajeer_logs TO cajeer_migrator`, после успешного `migrate` вернуть прежние права. Для чистой установки и обычных следующих миграций, если эталон уже создан, достаточно прав владельца app schema. Runtime не нужны DDL-права; он должен читать историю/эталон/журнал. Если используется отдельная migration role, убедитесь, что её default privileges дают runtime SELECT на новые служебные таблицы (старые инструкции выдавали SELECT/INSERT/UPDATE/DELETE на все app tables; можно отозвать ненужные изменения history/state/runs/attempts у runtime). Не отзывайте права владельца или права, необходимые реальным репозиториям.

```sql
-- Выполняет DBA/владелец таблиц, если роли разделены и не наследуют права друг друга:
GRANT SELECT ON cajeer.schema_migrations, cajeer.schema_migration_state,
    cajeer.schema_migration_runs, cajeer.schema_migration_attempts TO cajeer_runtime;
REVOKE INSERT, UPDATE, DELETE ON cajeer.schema_migrations, cajeer.schema_migration_state,
    cajeer.schema_migration_runs, cajeer.schema_migration_attempts FROM cajeer_runtime;
```

Если схема содержит сторонние таблицы/индексы, не удаляйте их автоматически. 0.1.2 использует строгий контроль выделенной схемы: перенесите сторонние объекты в другую схему либо внесите изменение через новую проверенную миграцию. Ручную потерю индекса/столбца/constraint исправляет DBA после проверки backup и исходного SQL. Затем `migrate:verify`; никакой команды «принять произвольный drift» нет. Старые backups 0.0.9/0.1.0/0.1.1 можно восстановить в отдельную пустую БД; restore проверит историю и выполнит такую же adoption. Данные и журнал backup 0.1.2 проверяются по сохранённому эталону.

## Команды и состояние

| Команда | Работа |
|---|---|
| `migrate:plan` | Read-only история, drift, список pending, режим, SHA-256, количество SQL statements, размер, категории операций, лимиты |
| `migrate:status` | Читаемый список applied/pending, integrity; код 0 только если текущая схема verified |
| `migrate:verify` | JSON структурной проверки, missing/changed/unexpected объекты и журнал; код 0 только для текущей verified схемы |
| `migrate` | Реальное выполнение pending SQL, либо одноразовая проверка и adoption старой БД; при ошибке ненулевой код |

`plan` возвращает 0 для uninitialized/unverified и обычных pending (это план, не сертификат готовности), 1 при drift. История с пропусками, несовпадающими контрольными суммами, неизвестными версиями или повреждёнными метаданными вызывает отказ. SQL-файлы нумеруются последовательно и не переписываются. Незавершённый backfill/concurrent-index нельзя удалить из следующей сборки: при несовпадении файла с durable journal runtime и мигратор останавливаются. `migrate` не редактирует каталог миграций, не выполняет downgrade и не выполняет автоматическое удаление объектов ради устранения drift; явно проверенный SQL может изменять данные и схему. Журнал не содержит SQL-параметров, паролей или текстов исключений PostgreSQL.

`/ready` и `db:doctor` отклоняют неподтверждённую, отстающую или изменённую схему. DB-backed HTTP (identity, ingest, поиск) и штатные CLI workers/maintenance удерживают shared session advisory lock на время операции. `migrate` использует exclusive lock с тем же ключом, включая промежуточные commits; PostgreSQL backup держит shared lock и не блокирует другие shared runtime-операции. В процессе миграции API возвращает 503, а worker может завершиться с ошибкой и быть перезапущен supervisor. Остановка сервисов остаётся рекомендуемой процедурой. Не используйте старые бинарники одновременно с новой миграцией, прямой DDL или PgBouncer transaction pooling; сторонние клиенты, не соблюдающие блокировку, не защищены. Диагностическая метрика `cajeerlogs_schema_verified` равна 1 только при текущей verified схеме.

## Транзакционная миграция

Каждый SQL-файл выполняется в отдельной транзакции, включая запись SHA-256 в `schema_migrations`, запись успешной попытки и новый эталон схемы. Если SQL падает, изменения этого файла откатываются целиком; ранее успешно завершенные файлы сохраняются. Повторный запуск продолжит с первого pending файла. Прерванная попытка отмечается `interrupted` при следующем запуске. Не допускаются `BEGIN/COMMIT/ROLLBACK`, произвольные `SET`, `DO`, функции и другие неразрешённые верхнеуровневые команды; SQL — доверенный код разработчика, а не безопасная среда для пользовательских запросов.

Поддерживаются обычные CREATE/ALTER/DROP таблиц, индексов, последовательностей и представлений, DML и SELECT. Не изменяйте служебные таблицы миграций внутри SQL, не используйте ссылки на жестко заданную schema в релизном SQL. Обязательны PostgreSQL session pooling или прямое соединение. Для больших DDL проверьте свободное место, блокировки, backup и заранее назначьте окно обслуживания. План — описание режима и операций, не автоматическая оценка времени или блокировок.

Лимиты задаются окружением CLI (не записываются в `.env`):

```sh
DB_MIGRATION_STATEMENT_TIMEOUT_MS=1800000 \
DB_MIGRATION_MAX_BACKFILL_BATCHES=1000 \
php bin/cajeer migrate
```

Timeout: 1 000–86 400 000 мс, default 600 000; batch limit: 1–100 000, default 1 000. `DB_LOCK_TIMEOUT_MS` от PostgreSQL Runtime по-прежнему ограничивает ожидание блокировок, в том числе общей advisory-блокировки; значение statement timeout восстановления сессии не меняется. Таймауты применяются на каждый SQL statement, не на весь upgrade. Мигратор требует writable primary с fsync=on и задаёт synchronous_commit=on для своих операций. Не редактируйте уже записанный checksum, даже если предыдущая попытка не завершилась; исправьте причину, восстановите проверенную копию при необходимости или выпустите новую согласованную процедуру исправления. При неопределённом COMMIT повторная команда проверяет durable history, а не повторяет завершённую операцию.

## Длительные индексы (явный режим)

Пример будущей миграции, **не добавлен в официальный набор 0001–0008**:

```sql
-- cajeer:concurrent-index
CREATE INDEX CONCURRENTLY idx_log_events_service_time ON log_events(service, occurred_at DESC);
```

Допускается одна команда `CREATE INDEX CONCURRENTLY`, обычные столбцы, btree (по умолчанию) или gin, явное новое имя; без UNIQUE, выражений, partial predicate, IF NOT EXISTS или ссылки на другую схему. Journal фиксируется до DDL, команда исполняется вне транзакции, потом проверяются `indisvalid`/`indisready` и соответствие таблицы. Завершение в истории и эталоне атомарно. Если процесс прерван после регистрации попытки и создания индекса, повторный `migrate` проверяет прежний эталон за исключением именно этого индекса, сверяет журнал/checksum/таблицу, убеждается, что индекс не UNIQUE/PRIMARY и не обслуживает constraint, затем выполняет `DROP INDEX CONCURRENTLY` и заново создаёт индекс. Так восстанавливаются invalid и valid-but-unrecorded индексы без предположения, что валидный индекс имеет правильное определение. Уже существующее имя без предыдущего журнала не удаляется. Для неподдерживаемых форм нужен отдельный согласованный DDL/план DBA.

## Длительный backfill (явный режим)

```sql
-- cajeer:backfill
WITH batch AS (
  SELECT id FROM demo WHERE value IS NULL ORDER BY id LIMIT 1000
)
UPDATE demo SET value = 'filled'
FROM batch WHERE demo.id = batch.id AND demo.value IS NULL
RETURNING demo.id;
```

Пример для будущей миграции на подготовленной таблице `demo`. Один CTE с LIMIT, один основной UPDATE с WHERE и RETURNING. В каждом проходе отдельная транзакция, максимум 10 000 изменённых строк (превышение откатывает этот batch); при достижении лимита проходов команда останавливается с ненулевым кодом, ранее committed batch сохраняются. Следующий запуск повторяет выражение с текущими данными, а счётчик batch продолжается. Когда затронуто 0 строк, миграция отмечается применённой. **Автор SQL обязан обеспечить идемпотентное условие и детерминированную выборку; синтаксический анализ не доказывает семантику произвольного UPDATE.** Не используйте `SKIP LOCKED`, если нулевой результат может означать только временную блокировку строк, и не выполняйте внешние эффекты. Большие backfill не атомарны целиком; runtime при pending блокируется до окончания. Работайте с backup и окно обслуживания.

## Область структурной проверки

Сверяются relation kind, persistence, RLS, partition metadata, имена/типы столбцов, nullable/default/generated/identity/collation, ограничения и их validation/enforcement, индексы (метод, колонки, порядок, opclasses, предикат, valid/ready/live), последовательности и их параметры/ownership, пользовательские triggers, policies и функции. Не сравниваются количество строк, значения последовательностей, PostgreSQL OID обычных объектов, владельцы и ACL, статистика, tablespace/physical tuning. Это drift-контроль управляемой схемы, а не независимая security-attestation против владельца БД. Изменения версии PostgreSQL/deparser могут потребовать проверенного отдельного плана major upgrade; автоматический `rebaseline` не предусмотрен. Readiness и runtime-проверки читают фактический каталог; измерьте нагрузку на вашей БД. Не включайте сторонние объекты в управляемую схему.
