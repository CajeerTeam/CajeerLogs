# CajeerLogs 0.9.9 — Live Load Testing & Performance Certification

## Что исполняется

`scripts/load_test.py` — самостоятельный Python 3.10+ клиент (только стандартная библиотека), который отправляет **действительные** подписанные HTTP-запросы на работающий CajeerLogs с PostgreSQL и workers. Он не объявляет синтетические ответы признаком производительности.

| Профиль | Реальная нагрузка | Проверка |
|---|---|---|
| `sustained` | Равномерная подача на выбранной частоте | Latency, стабильность подачи, успех записи и реальное чтение из БД |
| `stress` | Три последовательных участка с частотой `rate`, `2×rate`, `4×rate` | Работа под увеличенной конкуренцией, отсутствие невидимых потерь |
| `soak` | Длительная равномерная подача | Весь заданный интервал, p50/p95/p99, error rate, отказ от бесконечного буферизования futures |
| `fault` | Реальные запросы через локальный reverse proxy, которые перенаправляются к указанному HTTPS origin | Реальные 503 и 429 перед отправкой, *потеря ACK после обработки upstream*, инъекция задержки; корректные повторы и отсутствие дублей |

Каждый POST имеет собственный `Idempotency-Key`, тело неизменно при retry, HMAC nonce и timestamp пересоздаются для каждой попытки. Асинхронные запросы проверяются по статусу job до `completed`; все синхронные и асинхронные квитанции сверяются с множеством ID событий и исходным содержимым (проект, источник, уровень, текст) через страницы `GET /api/v1/logs?project_id=...&request_id=...`. Проверка проваливается при нехватке или появлении лишних записей, дубликатах, незавершённых jobs, нарушении SLA, превышении retry или недостаточной интенсивности подачи. Percentiles рассчитываются из каждого успешного запроса в миллисекундных корзинах: объём памяти для latency не увеличивается с числом запросов. `async_percent` по умолчанию 20%.

**Fault model:** 429/503 создаёт proxy до отправки запроса; lost ACK создаётся только после реального успешного HTTP ответа upstream и отбрасывания ответа. Этот тест проверяет сетевую устойчивость клиента, повторение с идемпотентностью на сервере и реальное сохранение. Он не заменяет убийство процессов PostgreSQL/worker или дисковые сбои. Тесты остановки и восстановления PostgreSQL и queue находятся в `tests/production_smoke.py` и обязательно выполняются при релизном Docker smoke.

## Запуск против изолированного стенда

1. Развернуть отдельный стек с PostgreSQL 17/18, работающим queue worker, HTTPS и **новым пустым проектом** с source `app`.
2. Выпустить API-токен для этого source с разрешениями `logs:write`, `logs:read` и с достаточными rate limits (иначе SLO корректно провалятся). Не передавать секреты через аргументы командной строки.
3. Убедиться, что worker завершает async tasks и нет чужой нагрузки. Для проверяемой сертификации необходимо иметь полный release archive 0.9.9 (не overlay обновлённых файлов).

```bash
export CAJEER_TOKEN='your-disposable-test-token'
export CAJEER_LOAD_TEST=1
# Если включена отдельная версия HMAC v2:
# export CAJEER_SIGNING_KEY_ID='uuid-of-signing-key'
# export CAJEER_SIGNING_SECRET='sk_<64 hex characters>'

python3 scripts/load_test.py \
  --url https://logs-staging.example.test \
  --project '11111111-1111-4111-8111-111111111111' --source app \
  --rate 8 --batch 20 --concurrency 16 --async-percent 100 \
  --sustained-seconds 120 --stress-seconds 180 \
  --soak-seconds 1800 --fault-seconds 120 \
  --p95-ms 2000 --fault-p95-ms 4000 --max-error-rate 0.01 \
  --min-rate-ratio 0.95 \
  --archive /safe/path/CajeerLogs-0.9.9.zip --certify \
  --output /safe/path/performance-certification.json \
  --confirm-disposable
```

Опционально указать `--ca-file /path/to/test-ca.pem`, если это частный CA. Сценарий `--scenario fault` можно выполнять отдельно, он всегда выдаёт `certified: false` (диагностический профиль). Максимум 64 потока, rate ≤2000 запросов/с, batch ≤100 событий, 2 млн запросов на фазу, таймаут ожидания drain ограничен; для высоких скоростей увеличивайте `--max-requests`, сравнивайте с фактическими квотами БД, token bucket, network и параметрами приложения. Если достигнут cap до окончания интервала, gate падает.

В версии 0.9.9 `--certify` требует 100% async и batch >= 20, чтобы подтвердить именно путь PostgreSQL queue, а не только sync ingestion.

`--certify` требует *все четыре* профиля, продолжительность не меньше `60/120/900/60` секунд, полный архив с корректным SHA256-manifest и ответ `/ready` со статусом `ok` и версией `0.9.9`. Отчёт содержит фактический hash архива, тайминги, SLO threshold, status каждого gate и `certified` (true только если все условия пройдены). Это **результат конкретного запуска и нагрузки**, а не общая гарантия capacity/HA или независимая аккредитация. Отчёт не подписывается криптографически; доверие к нему зависит от защищённого CI-раннера и сохранения неизменённого evidence.

Пропущенное, ошибочное или изменённое содержимое даже при совпадающих UUID блокирует `persisted_payload` и `durable_consistency`. Измеренная задержка, статистика минутных окон и конкурентного поиска привязаны к одной фазе нагрузки; отчет не означает независимую сертификацию. В ходе реального production smoke дополнительно проверяются `security:audit`, `operations:triage`, приватный снимок инцидента, остановка worker и PostgreSQL, срабатывание Prometheus и восстановление операций; финальный release gate требует эти свидетельства вместе с performance-отчетом.

## Автоматизированные проверки релиза

- `python3 tests/load_test.py` — executable self-test клиента на контрольном HTTP сервере, включая потерянные ответы, retries, реальные поисковые ответы, негативные проверки целостности и отказ от ложной сертификации. Это **не** production benchmark.
- `python3 tests/production_smoke.py` — отдельный Docker Compose/PostgreSQL/PHP-FPM/TLS стек (никаких mock API) и полный короткий прогон четырёх профилей, плюс реальные остановки/восстановления queue и PostgreSQL. Короткий прогон устанавливает только `status: passed`, **не** `certified: true`.
- Команда `scripts/certify.py release` требует успешного production smoke и database/admin матрицы; длительная performance-сертификация запускается отдельно на специально выделенном стенде с параметром `--certify`, внутри `scripts/certify.py release` на изолированном Docker-стеке.

**Безопасность:** HTTP допускается только для loopback; перенаправления отключены, bearer не переадресуется; нет переменных окружения с секретами в отчёте; слушающий fault proxy привязан исключительно к `127.0.0.1`. Runner нельзя направлять на продуктивную инсталляцию. Длительная нагрузка создаёт большие объёмы **постоянных** данных; после теста удалять только одноразовый проект/тестовую БД средствами штатной эксплуатации. Нет SQL-инъекций или утилит для намеренной порчи реальных дисков.
