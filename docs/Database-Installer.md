# Database & Installer 0.0.2

> Историческая инструкция. Для текущего установщика 0.1.5, раздельных ролей, статуса и восстановления администратора используйте [Installer & Administrator](Installer-Administrator.md).

## Требования и подготовка PostgreSQL

PHP 8.4+ с `pdo_pgsql`, поддержкой `password_hash(..., PASSWORD_ARGON2ID)`, PDO, ctype, filter, PCRE, JSON. PostgreSQL 17+. Composer не требуется для runtime/CLI. Установите PHP-FPM отдельно для production. Все поддерживаемые операции БД работают через PostgreSQL; остальные драйверы в репозитории не поддерживаются этим релизом.

Установщик CajeerLogs не создаёт системного пользователя, PostgreSQL-кластер или роль суперпользователя. Создайте отдельную БД один раз от имени PostgreSQL-администратора. На Linux с локальным PostgreSQL, например:

```sh
sudo -u postgres psql
```

```sql
CREATE ROLE cajeer_logs LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password cajeer_logs
CREATE DATABASE cajeer_logs OWNER cajeer_logs;
\quit
```

Пароль вводится в `\password` интерактивно, а не в SQL-строке или истории shell. Для отдельной схемы заранее создайте её внутри новой БД с владельцем `cajeer_logs`. По умолчанию используется `public`. Не подключайте приложение к чужой схеме или роли с повышенными привилегиями. Роль должна владеть схемой/таблицами либо иметь права USAGE, CREATE и необходимые DML-права. Для 0.0.2 одна роль выполняет миграции и runtime; отдельный read-only/runtime role не настраивается автоматически.

## Установка

Выполняйте установку от пользователя приложения, который сможет читать `.env` (0600) и записывать `storage/`. Корень проекта должен быть доступен для создания и атомарной замены `.env` во время установки; после установки код можно сделать read-only для FPM. `.env` не публикуется через HTTP.

1. `cp .env.example .env` и `chmod 600 .env` (если файла ещё нет). Укажите `APP_ENV=production`, `APP_DEBUG=false`, реальный `APP_URL`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD`, `DB_SCHEMA`. Для удалённой БД используйте `DB_SSLMODE=verify-full`, `DB_SSLROOTCERT=/absolute/path/to/ca.pem`, совпадающее с сертификатом DNS-имя. `prefer` оставлен для локальной совместимости, не гарантирует TLS.
2. `php bin/cajeer install:check` проверяет runtime, Argon2id, подключение и CREATE в схеме. Отсутствие миграций на новой БД не ошибка preflight.
3. `php bin/cajeer install` — интерактивные реквизиты, email и пароль первого администратора (минимум 12 байт), подтверждение пароля. Если DB_PASSWORD уже установлен, он не запрашивается повторно. Для изменения настройте его в `.env` или окружении.
4. `php bin/cajeer migrate:status`, `php bin/cajeer db:doctor`, `php bin/cajeer doctor` должны завершиться с кодом 0.

Установщик проверяет соединение до записи `.env`, сохраняет эффективные DB-настройки, заменяет шаблонные/короткие секреты четырьмя независимыми криптографическими случайными значениями, сохраняет существующие валидные секреты и дополнительные переменные, затем запускает миграции и создаёт первого администратора. Формат `.env` нормализуется: комментарии и исходное форматирование заменяются. Не передавайте внешние шаблонные секреты в окружении. При ошибке после записи `.env` файл остаётся для повторного запуска; миграции атомарны, создание администратора выполняется отдельной транзакцией. Повторная установка с тем же email и правильным паролем идемпотентна; новый email или неправильный пароль не сбрасывает аккаунт. Никакие пароли не выводятся в отчётах.

### Неинтерактивная установка

Передайте DB_* в окружении или используйте `.env`. Передайте `CAJEER_ADMIN_EMAIL`, `CAJEER_ADMIN_PASSWORD` через секрет-хранилище CI/процесса, а затем:

```sh
php bin/cajeer install --non-interactive
unset CAJEER_ADMIN_PASSWORD
```

Пароль администратора не записывается в `.env` и не передаётся в аргументах командной строки. Не помещайте секреты в git, историю команд или CI-логи. Альтернативная команда: `php installer/cli/install.php`. Web installer намеренно запрещён.

## Миграции

```sh
php bin/cajeer migrate:status
php bin/cajeer migrate
php bin/cajeer migrate:status
```

`migrate:status` только читает историю (код 1 при pending/ошибке). `migrate` возвращает 0 при успехе или отсутствии pending. Миграции выполняются в одной транзакции под PostgreSQL advisory lock для выбранной схемы. Таблица `schema_migrations` хранит имя файла, SHA-256 и дату. Изменение уже применённого файла, неизвестная версия, пропуск номера или SQL-ошибка приводят к отказу; история и изменения откатываются. При конкуренции второй процесс ожидает блокировку до `DB_LOCK_TIMEOUT_MS`. Не редактируйте применённые файлы и не выполняйте SQL вручную; добавляйте последовательный `0003_*.sql` и далее. Миграции должны содержать транзакционно совместимый SQL, без собственного COMMIT/ROLLBACK, CREATE INDEX CONCURRENTLY и других нетранзакционных операций. Runner предназначен для доверенных миграций из релиза, не для произвольных пользовательских SQL-файлов.

При обновлении 0.0.1 (где рабочей БД не было) используйте чистую БД. Если вы вручную создали старую схему без истории, автоматическое присоединение не выполняется: установщик остановится при конфликте таблиц, не удаляя данные. Сделайте backup и отдельно перенесите данные в чистую 0.0.2 БД; не вставляйте вручную фиктивные записи в историю. Перед будущими обновлениями выполняйте `pg_dump`, проверяйте восстановление и тестируйте миграции на копии БД.

## Диагностика

- `/health`, `/api/v1/health` — PHP runtime, независимо от доступности PostgreSQL.
- `/ready` — HTTP 200 при доступной БД, актуальных миграциях, наличии доступных для чтения и записи таблиц; 503 в противном случае. Не подтверждает наличие рабочего ingestion или HTTP-auth.
- `db:doctor` — версия PostgreSQL, история, pending, безопасная диагностика БД.
- `doctor` — preflight, HTTP dispatch и диагностика PostgreSQL.
- `system:report` — JSON runtime+database; код 1 при проблемах.
- `/metrics` — метрики PHP runtime, не доказательство готовности БД.

`DB_CONNECT_TIMEOUT` (секунды, 1–60), `DB_STATEMENT_TIMEOUT_MS` и `DB_LOCK_TIMEOUT_MS` (1–600000 мс) ограничивают ожидание. Значения по умолчанию 5 с / 30 с / 10 с; для больших миграций настройте их осознанно. Соединения непостоянные, в UTC, UTF-8, с native prepared statements; схема должна быть доверенной.

## Локальный Docker Compose

Только для разработки, с отдельным PostgreSQL-суперпользователем и application-role. Сгенерируйте два независимых пароля и экспортируйте их (Linux/Bash):

```sh
export POSTGRES_ADMIN_PASSWORD="$(openssl rand -hex 32)"
export DB_PASSWORD="$(openssl rand -hex 32)"
export LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)"
docker compose up -d --build
docker compose exec app php bin/cajeer install
docker compose exec app php bin/cajeer db:doctor
curl -i http://127.0.0.1:8080/ready
```

Сохраните пароли безопасно для повторного запуска Compose; они нужны каждый раз при интерполяции файла. PostgreSQL volume сохраняет данные. Скрипт инициализации роли выполняется только при первом создании volume; изменение env не меняет существующие пароли БД автоматически. Не удаляйте volume, если нужны данные. App использует bind mount и пишет `.env` в проект, с `DB_HOST=db` и `APP_ENV=local`; этот `.env` предназначен для Compose, не для прямого запуска на хосте. Встроенный сервер не предназначен для production.

## Тесты

```sh
php tests/runtime.php
php tests/database_config.php
python3 tests/http_runtime.py
php bin/cajeer openapi:lint
# Экспортируйте DB_* для отдельной тестовой БД с правом CREATE SCHEMA:
CAJEER_TEST_DATABASE=1 php tests/database.php
```

Интеграционный тест создаёт случайную схему, запускает CLI-установщик на временной копии проекта, проверяет историю, откат, конкурентную блокировку, репозитории, хеши токенов, повторную установку и readiness, затем удаляет только созданную тестовую схему. Не запускайте на production. CI поднимает PostgreSQL 17 и проверяет PHP 8.4/8.5. Локальный тест конфигурации не требует PostgreSQL.
