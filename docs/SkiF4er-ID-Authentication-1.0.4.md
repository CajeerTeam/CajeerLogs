# Дополнительный вход через SkiF4er ID

> Добавлен в 1.0.4. В 1.0.5 появилась [самостоятельная привязка и управление сессиями](Identity-Linking-Security-1.0.5.md).

Интеграция использует серверный OpenID Connect и известный issuer `https://id.skif4er.ru/realms/skif4er`. Страница [SDK SkiF4er ID](https://id.skif4er.ru/sdk/) при разработке была недоступна, поэтому неподтверждённые методы SDK не используются. Адреса авторизации, токенов, JWKS и UserInfo получаются через discovery с ограничением HTTPS-хоста и realm. Для реального входа нужен зарегистрированный клиент и проверка у провайдера.

## Настройка

1. Создайте резервную копию, примените штатные миграции `0034_skif4er_auth.sql` и последующие (включая `0035_skif4er_linking.sql`). Не меняйте ранее применённые миграции.
2. Зарегистрируйте конфиденциальный веб-клиент в SkiF4er ID: Authorization Code, PKCE S256, RS256, `client_secret_basic`, области `openid profile email`, подтверждённый email. Укажите **точный** HTTPS callback: `https://YOUR-CAJEERLOGS-HOST/api/v1/auth/skif4er/callback`, с фактическим префиксом API. Не используйте шаблоны произвольных адресов, implicit grant или password grant.
3. В закрытой конфигурации задайте значения и перезапустите службы:

```dotenv
SKIF4ER_ID_ENABLED=true
SKIF4ER_ID_CLIENT_ID=your-client-id
SKIF4ER_ID_CLIENT_SECRET=your-client-secret
```

Вместо секрета нативная установка поддерживает `SKIF4ER_ID_CLIENT_SECRET_FILE` с приватным абсолютным путём. Настройте HTTPS `APP_URL` и доверенный прокси. Не раскрывайте секрет в клиентском коде или Git.

4. В версии 1.1.0 пользователь может явно связать аккаунт в настройках профиля. Доверенный оператор также может получить стабильный `sub` по проверенному административному каналу провайдера и привязать существующий аккаунт:

```sh
php bin/cajeer auth:skif4er-bind operator@example.org VERIFIED_SUBJECT --confirm
```

Не используйте email, имя или непроверенный токен в качестве идентификатора. Команда не создаёт пользователя, не повышает права и не заменяет существующую привязку скрытно.

5. Откройте `/admin/` по HTTPS и нажмите «Войти через SkiF4er ID». После входа у провайдера подтвердите локальный вход и локальный TOTP/код восстановления, если настроено. Создаётся обычная локальная сессия с текущими полномочиями. Сохраняйте независимый локальный административный вход.

## Защита и отказоустойчивость

Проверяются подпись RS256, issuer, audience, nonce, срок действия, PKCE, случайный state и одноразовое завершение. Временная cookie имеет `Secure`, `HttpOnly`, `SameSite=Lax`, привязана к хосту; локальные сессии сохраняют `SameSite=Strict`. Попытка ограничена пятью минутами и числом проверок второго фактора. Токены провайдера не сохраняются и не возвращаются браузеру. Роли провайдера не заменяют локальный RBAC; email не связывает аккаунты автоматически.

Не записывайте строку запроса callback и заголовки Authorization/Cookie в прокси-журналы. При отказе провайдера используйте локальный вход; отключение — `SKIF4ER_ID_ENABLED=false` и перезапуск. Глобальный выход SSO, обновление токенов и распространение отзыва сессии у провайдера не заявлены.

## Приёмка

Подтвердите discovery, реальный вход с зарегистрированным клиентом, отклонение неизвестного субъекта и заблокированного аккаунта, ошибочного TOTP, отмены и повторного callback. Проверьте локальный парольный вход независимо от внешнего сервиса. Локальный тест не подтверждает доступность провайдера.
