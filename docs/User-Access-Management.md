# User & Access Management — 0.3.7

Раздел «Пользователи» доступен только администратору с активной cookie-сессией. Поиск по email, имени и UUID выполняется на сервере; роль, статус и 2FA комбинируются. Страницы используют UUID keyset; доступна сортировка по email и дате создания. Карточка загружает актуальные метаданные, сессии, список проектов и историю доступа. Редактирование передаёт `expected_updated_at`; старые API-клиенты могут не передавать это поле. Конфликт требует обновления карточки. Изменение аккаунта отзывает сессии, последнего пригодного администратора блокировать или понижать нельзя.

## Проекты и роли

Глобальные роли: administrator, operator, viewer. Администратор имеет неявный доступ ко всем проектам, даже без членства. У operator/viewer необходима запись членства; проектная роль viewer ограничивает operator, operator не повышает viewer. Заблокированный аккаунт не имеет эффективной роли. В карточке можно найти проект и назначить/изменить/удалить членство; в проекте можно найти пользователя по email вместо ручного UUID. Изменения применяются сервером к последующим запросам. Архивирование и существующие ограничения операций проектов сохраняются.

## API v1

- GET /users?q=&role=&status=&two_factor=&sort=&limit=&cursor= — фильтры all/administrator/operator/viewer, all/active/blocked, all/enabled/disabled.
- GET /users/{user} — публичные метаданные аккаунта (без хешей и секретов).
- GET /users/{user}/projects — явное членство и эффективные роли; администратору также неявные проекты.
- GET /users/{user}/audit — история операций доступа, от новых к старым, cursor UUID; произвольный context не возвращается.
- POST /users/{user}/2fa/reset — пароль действующего администратора и его TOTP/recovery при включённой 2FA; CSRF обязателен. Нельзя сбросить собственную 2FA этим маршрутом. Секрет, recovery-коды и сессии целевого пользователя удаляются транзакционно. При обязательной 2FA администратор заново проходит enrollment. Сброс фиксируется в audit_log.

Миграции 0001–0016 неизменны; обновление не требует новой миграции. API-токены являются отдельными credentials и не отзываются при изменении пользовательского членства или сбросе 2FA; используйте управление токенами. Сортировка каталога UUID, email (ASC/DESC) или дата создания (DESC), аудит — created_at DESC/id DESC. Не обещается неизменяемый snapshot каталога. Проверки PostgreSQL и полная CI-сертификация обязательны перед production deployment.
