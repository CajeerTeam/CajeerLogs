# Audit Log & Accountability — 0.4.4

## Upgrade and operation

Stop application writers, take a verified database backup, overlay the 0.4.4 files, run `php bin/cajeer migrate`, `php bin/cajeer migrate:verify`, `php bin/cajeer audit:verify` and `php bin/cajeer doctor`. Migration 0019 extends `audit_log`, attributes existing records, builds a historical baseline in chronological order, and installs append-only triggers. Migrations 0001–0018 are unchanged. The backfill runs in a single maintenance transaction; test its duration and disk/WAL budget on a copy of large audit histories before upgrading.

## Access and query

The Security & Audit workspace and existing project/system audit panels expose result (success, failure, denied), actor type (user, token, system, anonymous), exact action, actor/target UUID, and UTC from/to (inclusive/exclusive). Project audit requires a session and `audit:read` in that project; global audit requires Administrator. Denials of cross-project access are global events, not visible to the target project's operators. Machine credentials cannot read audit. Global chain positions and hashes are exposed only in the global audit, not project pages, to avoid revealing cross-project event volume. Never expose raw context. Historical scope derives from existing explicit project_id metadata and documented project/member actions; legacy events lacking attribution remain global. The same permission allows bounded NDJSON export of the filtered page; use `X-Next-Cursor` for subsequent pages. Each export is audited. `format=ndjson` returns up to 100 records, not a full database dump. The UI downloads the first filtered page of up to 100 and reports when more exist.

## Integrity

Each row has a consecutive `chain_position`, `previous_hash` and SHA-256 `event_hash` over its typed metadata and JSONB context. PostgreSQL serializes appends per schema with a transaction advisory lock. A committed mutation and its existing audit insert share the controller transaction. Authenticated 403 responses are recorded after rollback; login failures and reauthentication failures retain their existing independent recording. Log exports and audit exports are recorded before returning the response. CLI retention policy changes are recorded atomically. The chain includes all audit rows, not only those visible to an individual project.

Run `php bin/cajeer audit:verify` from a trusted operator shell. Output includes `valid`, `entries`, `invalid`, `head_position`, `head_hash`, and `checkpoint_matches`. A mismatch exits nonzero. Store the position and hash in an independent protected location (for example a signed operations record or immutable object store). Later run `php bin/cajeer audit:verify POSITION HASH` to verify that prefix and all subsequent entries. An old valid checkpoint remains valid as new events append. An empty chain has position 0 and a zero hash. Do not treat a fresh checkpoint from a suspected compromised database as proof of integrity.

Triggers reject UPDATE, DELETE and TRUNCATE, including normal runtime table-owner DML. A sufficiently privileged database owner/superuser can disable triggers or replace functions; this is not WORM storage or cryptographic nonrepudiation. Hashes alone cannot prove the completeness of history before the baseline or detect a malicious rewrite of the whole chain without a trusted independent checkpoint. Use a restricted non-owner runtime role and grant only SELECT/INSERT on audit_log; remove inherited UPDATE/DELETE/TRUNCATE grants with DBA-managed SQL as appropriate. Function/trigger changes are included in schema integrity snapshots. The backup restore fence verifies the restored chain before publication. Keep old checkpoints for the appropriate backup prefix; restored branches may diverge from a later checkpoint of the original instance.

## Retention and failure handling

No automatic deletion of the audit chain is enabled: ordinary log retention does not affect audit. Segmented archival/retention with signed checkpoints is deferred; do not disable triggers to prune production history. Monitor database size and back up audit with the existing PostgreSQL backup. Verification scans the full chain, so run it from maintenance tooling with a suitable database statement timeout. A failure of a transactional audit write fails the corresponding mutation; audit is not a best-effort logging call. Authorization denials are intentionally global and may increase audit volume. Existing API rate limits bound authenticated requests. No request body, bearer secret, password or TOTP seed is included in the new events. Raw legacy context remains in the database; only allowlisted metadata is exposed through the API.

## Tests

`tests/audit_database.php` requires a disposable PostgreSQL database (`CAJEER_TEST_DATABASE=1 APP_ENV=test`) and is part of the exact-release certification matrix. It tests historical migration, append-only behavior, rollback, integrity detection and independent checkpoint validation, project filtering and export authorization. Full production certification also requires the existing database/browser matrix and Docker smoke.
